# 快速模式设计

作者最常用的模式，**先于完整群组讨论实现**。完整群组见 [group-design.md](group-design.md)，两者共用底座。

## 1. 要解决什么

平常大部分问题是：给一个具体任务，一个主模型干活，另一个模型审，然后改掉问题。不需要开会。要快，要有依据，作者始终是最后把关人。

## 2. 五个步骤和文件交接

每次运行在当前项目的 `.mindfs/runs/<运行ID>/` 下交接。下一位 Agent 收到简短指令和项目相对路径。作者在阶段对话中实时看到模型报告的进展和交付正文；后台提取控制块，并保存可阅读的交付文档。审核员按任务和候选路径查看源码，需要比较时再读相关文件的局部差异。

| 步骤 | 读取 | 交付 |
| --- | --- | --- |
| 1. 主模型实现 | `00-任务说明.md` 中的原始任务、约束及附件路径 | `01-初次实现说明.md`，记录实现与自测。此步骤只执行一次。 |
| 2. 只读审核 | 本轮 `02-审核依据.md`，其中引用原始任务、初次实现说明和本轮改动清单，列明适用规范 | `02-审核意见.md`，保留意见原文、编号、文件和行号。 |
| 3. 主模型逐条回应 | 本轮审核意见与涉及的源码 | `03-逐条回应.md`，记录已修改的位置和未达成一致的理由。 |
| 4. 作者裁决 | 原审核意见与主模型回应 | 有分歧时生成 `04-作者裁决.md`，保存每条决定和自定义说明。 |
| 5. 最终修改与测试 | 实现说明、审核意见，以及存在的回应与裁决 | `05-改动结果.md`，按编号记录结果、改动文件和测试。作者可点文件查看对应回合的差异。 |

步骤 2 至 5 的文件保存在 `第01轮/`、`第02轮/` 等目录中。第 5 步完成后停止。作者点「再审一轮」可以补充意见、上传附件，提交后回到第 2 步。意见与上传后的附件路径写入本轮 `00-作者补充意见.md`，供审核员与上一轮意见、改动结果、回应和裁决一起核查。审核员逐条标明旧意见已解决或仍存在，新问题接着使用新编号，各轮交付文件保留。

## 3. 已定的决定（作者 2026-11-25）

- 审核模型只给意见，不改代码。
- 驳回审核意见**必须经过作者**。主模型不能自己驳回、也不能悄悄忽略任何一条。
- 每轮完成后运行项目已有的测试或构建，由作者决定是否复核。
- 规范依据：作者的 skill 和 `AGENTS.md`。
- 先做快速模式，再做完整群组。
- 参与的模型组合用**模板**配置，模板是**全局**的（所有项目共用），见 4.7。
- **每个阶段可展开实时执行过程并人工干预**：直接复用现有 `SessionViewer`（思考、工具调用、Diff、终端输出、`AskUser`），不重复造轮子。
- **阶段间以项目内交付文档解耦**：每个阶段给下一阶段交付的都是一份落地在项目目录内（`.mindfs/runs/<run-id>/`）的文档，而不是口头一句“我写好了”；这样任意阶段经过人工干预后，下游仍只需读取上游交付文档，流程不受影响。过程文档结束后如无留存意义，支持直接删除清理。

## 4. 设计要点

### 4.1 阶段交付文档与审核文档

- 审核员按只读权限读取源码与交接文件，后台原子写入本轮审核意见。工作区观察排除 `.mindfs/` 交接文件。
- **结束后清理**：过程文档仅服务于本轮流转，任务结束后界面提供“一键清理过程文档”（或由模型/后台直接删除整个 `.mindfs/runs/<run-id>/` 目录），也支持勾选保留特定文档，避免残留无用文件或污染 Git。
- **审核文档（`02-审核意见.md`）结构要求**：
  - 每条意见带：维度（功能 / 规范）、严重程度、文件和行号、说明。规范类的意见必须写明引用的是哪条规则（来自哪个 skill 或 `AGENTS.md` 的哪一节）。
  - 文件和行号由后台自动检查是否存在；不存在的标出来，让主模型和作者都能看到“这条出处查无此处”。
  - 末尾带隐藏的控制块，只放机器要读的结论（条目列表）；移植 tarobird 的控制块过滤器，只对这类回复启用。

### 4.2 “驳回必须经过作者”怎么保证

- 主模型的回应也是结构化的：审核文档里**每一条**都必须有一条回应，只能是“认同并已改”或“有疑问并附理由”。
- 后台机械检查条数：回应缺了任何一条，就算未完成，不进入下一步，也不当成“认同”。
- 回应格式解析不出来的，一律按“有疑问”处理，交给作者；绝不默认成“认同”。
- 给作者看的分歧界面把双方并排：审核模型怎么说、依据是什么；主模型怎么说、依据是什么。作者逐条选“按审核改”“不改”“其他指示”。
- 防止主模型全盘接受：主模型对“认同”的条目也要写明改了哪里；作者最后看到的是真实 Diff。

### 4.3 规范依据

- 审核提示里指明要读 `AGENTS.md` 和作者的 skill，规范类意见必须引用规则。
- **待确认**：作者说的“我的 skill”具体指哪些，以及 Claude、Codex、Gemini 各自怎么读到这些 skill（读不到就把相关内容放进审核提示）。这一点实现前必须弄清，不能假设每个 Agent 都能直接读到。

### 4.4 只读保障

沿用 [group-design.md](group-design.md) 第 8 节“步骤 0”的决定：先实测各 Agent 在只读档位下能否改文件；能只读的用原生只读，不能的用审核前后的工作区对比兜底，发现改动就提示作者。已知 ACP 类 Agent 目前的只读开关是空实现。

### 4.5 改完后的检查

- 运行哪些测试或构建，来自 `AGENTS.md` 和任务本身，不由我们硬编码。
- 结果如实汇报：通过、失败、跳过，各自写明。跳过不记为通过。
- 测试失败时**不自动再改一轮**，把失败输出交给作者决定。

### 4.6 审核材料

- `本轮改动清单.md` 从现有「本轮修改了 N 个文件」的会话记录提取路径，同时覆盖工作区观察和 Agent 原生报告。路径合并去重，保留采集不完整的提示。任务描述用于判断相关性与发现漏做的部分。
- 初审覆盖从实现开始的改动。复核覆盖上次审核结束后的逐条回应、人工干预、最终修改等回合。第 5 步另展示整个运行的改动文件，用户点选一个文件后查看对应回合的差异。

### 4.7 模板（快速模式与群组共用）

目的：模型组合是作者的个人习惯，不该每次任务都重新配置。使用方式是：选一个模板，直接说任务。

- **范围：全局**（作者 2026-11-25 确定）。所有项目共用，保存在用户级配置里，不放进项目目录。规范依据本来就来自各项目的 `AGENTS.md`，不需要靠模板区分项目。
- **模板内容**：每个成员的 Agent、模型、思考强度，以及角色。
  - 快速模式模板：主模型可以选择原生权限档位，空档位沿用 Agent 配置。审核模型由运行时强制只读。模板列表、编辑表单和本次运行独立显示权限档位。
  - 群组模板：成员列表，以及“最终文档作者”“轮次上限”这类群组设置。
  - 模板标明自己属于哪种模式。
- **默认模板**：每种模式可设一个默认模板，打开就能直接说任务。
- **应用后可修改**：改动只对本次运行生效，不影响模板。可选“保存为新模板”或“覆盖原模板”（一键保存）。
- **应用是复制，不是引用**：每次运行把当时的成员配置记在这次运行里。以后修改或删除模板，不影响历史记录。
- **模板里的模型可能已不可用**（Agent 没装了，或中转站不再提供该模型）：应用时逐个成员检查，不可用的明确标出，由作者自己选替代，**不悄悄换成别的模型**。
- 模板里的 Agent 和模型一律用 CLI 原生的标识，不用展示名。
- 持久化：具体存储格式实现时按现有偏好与供应商配置的做法确定（未核对）。无论用文件还是数据库，都要有版本或幂等迁移，并有旧结构升级的回归测试，只用临时数据（见 `AGENTS.md`）。

## 5. 与完整群组共用的底座

- 成员槽位：同一个会话里同一 Agent 的不同模型各自独立保活（进程池按成员隔离）。
- 审核文档的保存与出处检查。
- 控制块过滤器（移植）。
- 只读实测与事后检查。
- 模板：全局模板的保存、应用、不可用成员检查（见 4.7）。
- 持久化：新增记录用幂等迁移，必须有旧库升级回归测试，只用临时数据库（见 `AGENTS.md`）。快速模式只需要“一次运行”和“每条意见的回应”这类最小记录，完整群组的表以后再扩。

## 6. 实施步骤

**Q0：验证前提（不写产品代码）**
- 在临时目录实测各 Agent 的只读能力。
- 拿作者一个真实任务，手工按第 2 节流程跑一遍，看审核意见质量、主模型是否倾向全盘接受或随意驳回。结果决定设计是否调整。
- 弄清第 4.3 节的 skill 问题。
- 弄清独立界面外壳与组件复用的三个前提（见 [ui-design.md](ui-design.md) 第 9 节）：阶段/成员会话如何在后端创建与归属到运行记录且不出现在普通单聊列表里、卡片活动行的订阅开销、现有 `SessionViewer` + `SessionActivity` + `ActionBar` 在窄右栏（约 300px 起）下的实际可用性。

**Q1：底座**
成员槽位与进程池隔离、审核文档保存与出处检查、控制块过滤器、全局模板的存储与应用（含不可用成员检查）、最小持久化与旧库迁移测试。

**Q2：流程**
干活 → 审核 → 逐条回应 → 分歧问作者 → 修改 → 测试 → 报告的状态机，含条数检查与“解析失败按有疑问”。

**Q3：界面**
发起快速模式（选模板并直接说任务，可临时修改成员，一键保存或覆盖模板）、审核文档查看、分歧并排与逐条决定、最终测试结果。具体界面细节到这一步再问作者。

每一步完成后，分别记录“源码完成”和“验证通过”，写明验证范围，不沿用旧结论。

## 7. 不做的事

- 审核模型改代码。
- 自动多轮复审、测试失败后的自动返工循环。
- 主模型自己驳回审核意见。
- 其余见 [group-design.md](group-design.md) 第 9 节。

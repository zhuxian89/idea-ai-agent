# 多模型群组讨论：设计

## 1. 要解决什么

现在每次只有一个 Agent 在干活，不同模型各自的长处用不上。作者要的是像开会一样：把 Claude、Codex、Gemini 等拉进一个群，对一个需求各抒己见，最后收敛成一份方案；方案定了之后，一个人实现，其余人审。人站在最后做 review。

成员以“槽位”为单位，可以同一家的不同模型（如 Opus 与 Sonnet），不拘泥于厂家。

**最重要的要求：不盲从。** 多个模型顺着说时，后发言的容易附和前面的。设计的核心就是在流程上防住这件事。

## 2. 防盲从机制（核心）

1. **首轮盲评。** 每个成员只看到用户的问题和代码库，不告诉它其他成员的草案路径，各自读代码，各出一份文档。做不到硬隔离，用事后检查标出越界读取（见 3.1）。
2. **文档要有依据，后台自动检查。** 每条结论带文件和行号，后台检查出处是否存在，不存在就标出来。目的是不靠猜。
3. **立场变化可追溯。** 文档定稿后不能悄悄改，改就出新版，并写明为什么改。能看出谁是被说服的，谁只是随大流。
4. **互评时“同意”必须有内容。** 同意要写明检查了什么、剩下什么风险；反对要指出具体点。只写“我同意”不算有效表态，按没表态处理。解析不出来的表态一律算“未确认”，不默认成同意或通过。
5. **分歧不被抹平。** 最终文档固定有“未解决的分歧”一节：谁坚持什么、依据是什么。
6. **最终文档的作者被核对。** 每次讨论开始时由用户指定一个成员来写最终结论文档；写完后其他成员确认“我的观点被准确表达了吗”，没确认的标出来。
7. **一轮一停，到上限转人工裁决。**（作者 2026-11-26）每轮结束后停下，作者看过后点「开始下一轮」。没讨论好或作者人工介入过，都靠开下一轮继续。作者插话先落成文件，再进入下一轮。**到轮次上限（默认 3 轮，放在群组模板里可改）仍有分歧时，由作者裁决，不再靠模型继续讨论**，规则见 3.3。
8. **建议混用不同厂家。** 同一家的模型偏见更接近，更容易一起附和。这是提示，不是限制。

人始终在最后：用户 review 最终文档并拍板。

## 3. 讨论流程

1. 用户提出需求（可附 IDEA 代码选区），选择参与成员和本次的“最终文档作者”。
2. **第 1 轮（盲评）**：所有成员并行，各出一份文档。正文就是文档，由后台保存；末尾带隐藏控制块（见第 5 节），只放机器要读的结论（立场等）。
3. **第 2..N 轮（互评）**：每个成员拿到上一轮的文件，逐条回应：同意（附检查内容与剩余风险）或反对（附依据），必要时出自己的新版文档。上下文传文件路径，不贴全文，成员用自己的原生工具读。
4. 每轮结束停下，作者点「开始下一轮」或拍板。到轮次上限仍有分歧时转人工裁决（3.3）。
5. 达成一致后，指定的作者写**正式计划文件**，其他成员确认。
6. 作者 review，点「交给快速模式」，正式计划作为快速模式的任务说明。

### 成员权限与重试

发起会议或编辑模板时可为各成员选择权限。默认「严格只读」，也可沿用 Agent 配置或选择 Agent 提供的档位。开会后使用本次保存的成员配置。

未交付的成员可单独重试。后台检查该成员的当前发言和原生会话，确认已停止后沿用同一个会话继续。其他成员的执行和已交付材料保留。

### 3.1 交接铁律（作者 2026-11-26）

1. **每次交接都是文件。** 每个成员的草案、每轮的同意点与异议点、作者的插话、最终的正式计划，全部落成项目内文件。下一轮的模型只收到本阶段任务和文件路径，不依赖聊天记录。
2. **聊天框不隐藏原生文字。** 只过滤 `mindfs-control` 控制块。文字给作者看，文字加文件才是给下一轮的。
3. **首轮草案当场落盘，盲评靠“不告诉路径、事后可查”。**（作者 2026-11-26 修订：不做暂存区，成员有原生文件工具和 Bash，项目外目录挡不住，隔离只是假象。）草案交付时立刻写进项目的 `01-独立提案/<成员>.md`。首轮提示词只给本人的输出路径，并写明本轮不要读其他成员的草案和会话记录。后台读取各成员的工具调用记录，若盲评期间读到了其他成员的草案，在卡片上标出，由作者判断是否采信。群组里关闭单聊的 `prependSwitchHint`。
   读取标记依据成功的工具事件，识别明确的草案读取路径、Shell 读取通配符匹配到的已落盘草案，以及同时返回草案路径和匹配正文的搜索结果。Claude `Glob` 只列出文件名时跳过标记。搜索完成事件省略工具类型时，沿用同一次调用开始时的类型。真实 Agent 的目录读取待验收。
4. **共识与分歧由后台按条目机械合并，不让模型转述。** 每个成员的互评文件按条目写立场：同意要写明检查了什么和剩余风险，反对要写依据。后台把各成员原文按条目号合并成 `03-共识与分歧.md`，保留谁说的、原话和出处，写文件的人不是某个成员，避免被某一方写偏。
5. **作者插话也落文件。** 写成 `04-作者补充.md`（可带附件路径）。后续各轮收到历轮补充及已交付的点名答复路径，主笔生成正式计划时还收到本轮补充与答复。

### 3.1.1 群聊形态（学自 tarobird，作者 2026-11-26）

已读 tarobird 的 `client-protocol/group-discussion.ts`、`gateway/group-discussion.ts`、`client/src/group-mentions.ts` 与群聊界面。要点：

- **群是一条共用会话。** 作者和每位成员的发言都进同一条时间线，成员各自保留自己的上下文。tarobird 的“独立评议”就是首轮并行作答、收齐后公开，之后按顺序轮流发言，后发言的人拿到前面成员的发言和立场。
- **立场结构化。** 每次发言末尾带立场块（提出、同意某提案编号、有异议、暂不表态），缺失或解析失败不算同意。只有所有成员明确同意同一个提案才提前结束。我们沿用这个思路，把提案编号换成条目编号 C1、D1。
- **盲评只靠提示词。** tarobird 对盲评轮的成员在提示里明确写“不要寻找、请求或推断其他成员的首轮回答”，由后台扣住不发，没有做文件系统隔离。这与本文 3.1 第 3 条一致。
- **`@` 点名。** 点名谁谁回答，不点名只记录；`@` 后面的名字在中文紧贴时也要识别，邮箱、`@Override` 这类不算点名，同名有歧义时让用户选。
- **作者插话**绑定到本次讨论，交给之后每一位尚未收到它的发言者。我们让它落成 `04-作者补充.md`，下一轮只读文件。
- **控制：** 暂停、继续、结束、重试单个成员；每次发言前后有系统分隔条，写明第几轮、谁、是否重新发言。

和 tarobird 不同的地方：tarobird 把前面成员的原文内联进下一位的提示；我们遵守 3.1 的铁律，只传文件路径，原文留在聊天流里给作者看。

### 3.1.2 为什么还要做：相对 tarobird 的差异（2026-11-26 对照源码核实）

只做它已经有的东西没有意义。以下四点是读它的 `hub/group-discussions.ts`、`gateway/group-discussion.ts`、`client-protocol/group-discussion.ts` 后确认它**没有**的，也是我们的价值所在：

| 维度 | tarobird | 我们 |
| --- | --- | --- |
| 结论去向 | 一段文字：全员同意某个提案，或各成员最后的立场。没有计划文件，不能交给实现 | 对齐后生成 `05-正式计划.md`，在同一页接着进入快速模式的五步 |
| 出处核验 | 没有文件、行号检查 | 后台检查每条依据的文件和行号，查无此处的标出来，消息脚注显示“出处已核实”或“出处 N 处查无此处” |
| 分歧结构 | 只有“全员同意同一个提案”或“保留各成员最后立场”两种结果 | 按条目拆成共识和分歧（C1、D1），每条列出各成员原话、同意几人、异议几人，并写成文件交给下一轮 |
| 整体位置感 | 只有“第 x/y 轮” | 顶部流程位置条：提案、互评、对齐、计划、实现，会议和实现是同一条线 |

**tarobird 的工程项，我们已有的底座（2026-11-26 对照我们的代码核实，更正此前“我们没有”的说法）**：

- **断线与重启恢复**：`collab/store.go` 的 `RecoverInterruptedRuns` 在启动时把中断的运行标为待继续，`ContinueRun` 恢复。会议沿用同一套，运行、轮次、成员状态都存后台库。
- **多设备一致**：状态在统一的独立后台，前端靠 `collab.run.updated` 事件同步，各设备看到同一份，不需要额外设计。
- **重试单个成员**：继续时只重新调度没交卷的成员，已落盘的跳过。快速模式第 3 步已有同类的“只补缺漏条目”逻辑。
- **权限边界**：三种协议的只读门禁加审核后的工作区事后检查，已有。
- **离线**：不做（作者 2026-11-26）。

会议按运行、轮次和成员持久化交卷状态。临时旧库回归已验证重复迁移、既有运行和会话绑定保留、新会议读写，恢复测试已验证跳过已交卷成员。 [验证记录](../2026-11-11-standalone-backend/standalone-backend-implementation.md#开大会第-01-轮审核修复与验证)

### 3.3 分歧收敛与人工裁决（作者 2026-11-26）

**为什么到上限就转人工。** 模型之间的僵局多半不是信息不够，而是各自坚持，再讨论只会重复，或有人为了和气让步，这正是要防的盲从。开会的目的是作者拍板，不是模型吵出结果。

- **一轮的含义。** 全员各发言一次算一轮。第 1 轮含并行提案和互评；第 2 轮回应分歧；第 3 轮带新证据做最后一次尝试。
- **每轮结束都会停下**，所以上限限制的不是“自动跑几轮”，而是同一个分歧作者最多再点几次下一轮。
- **到上限仍有未对齐的条目：**
  1. 底部主按钮变成「裁决」，显示“还有 N 项分歧未对齐，请你裁决”。「开始下一轮」降为次要的「再讨论一轮」，作者仍可选择，不设硬封顶。
  2. **没裁决完不能生成正式计划。** 每个未对齐条目作者选一项：采纳某位成员的方案、写自己的说明、或明确标为“暂不决定”。
  3. 裁决写成 `第N轮/作者裁决.md`，保留各方原话和出处，写入 `05-正式计划.md`。只有标为“暂不决定”的条目才留在计划的“未解决的分歧”一节。
  4. 交互沿用快速模式的分歧裁决（并排显示各方说法，逐条选择，缺一条不能提交）。
- **提前出口：僵持。** 某条分歧连续两轮里同一成员立场没变、也没有补充新的出处，标为“僵持”，第 2 轮结束时就提示作者可以直接裁决，不必等到上限。依据是第 2 节“立场变化必须写明原因”，没有新增机制。
- **轮数默认 3 不是测出来的。** 借鉴自 tarobird 的默认值，具体几轮合适要等步骤 0（真实需求手工试跑）后确定，所以放在模板里可改，不写死。

### 3.2 文件布局

```
.mindfs/runs/<运行ID>/
  00-会议议题.md
  第01轮/
    01-独立提案/<成员>.md     交付时即写入，盲评期间读到别人的会被标出
    02-互评/<成员>.md
    03-共识与分歧.md          后台合并，下一轮的输入
    04-作者补充.md            作者介入时才有
    作者裁决.md               到上限仍有分歧时由作者逐条裁决后生成
  第02轮/                     输入：上一轮的 03 与 04，以及相关提案路径
    ...
  05-正式计划.md              对齐后生成，交给快速模式
```

最终文档结构：结论方案；共识点；未解决的分歧（谁、坚持什么、依据）；采纳了哪些成员的依据；各成员对“被准确表达”的确认状态。

## 4. 实现加群审（讨论之后再做）

1. 用户指定一个成员为主刀，按最终文档实现。
2. 本轮结束后，用现有的 `turndiff` 取得真实改动，交给其余成员审。
3. **Reviewer 只给意见，不改代码。** 要改，必须用户同意后，由用户指定的成员去改。
4. 因此不做“Reviewer 打回后自动返工”的循环：给出意见后由用户决定。

## 6. 数据与持久化（高层）

- 参与成员用**全局模板**配置（作者 2026-11-25）：选模板后直接说任务，可临时修改成员，也可一键保存为模板。模板的详细规则见 [quick-mode-design.md](quick-mode-design.md) 4.7，群组模板额外带“最终文档作者”和轮次上限。
- 单聊会话完全不动，群组是新的会话类型。
- 新增成员槽位、讨论运行、每一步发言三类记录，放在 `session-list.db`，用幂等迁移（`CREATE TABLE IF NOT EXISTS` 加必要的幂等加列）。
- 成员每轮产出的文档与最终结论文档由后台写入**项目内**的本次运行目录（`.mindfs/runs/<run-id>/`），使各成员能直接用原生工具按项目相对路径读取，同时满足只读成员不直接写盘的约束；`turndiff` 与只读事后检查显式排除 `.mindfs/runs/<run-id>/`。讨论或实现结束后，支持一键清理或让模型直接删除无须保留的过程文档（可单独保留最终结论文档）。
- 对话记录的 `Exchange` 增加可选的成员标识字段，全部可省略，旧记录不受影响。
- 按 AGENTS.md：新增表和字段必须有旧库升级回归测试（旧结构库可读写、重复迁移成功、已有会话和绑定保留），只用临时数据库。打包前跑 `kanban` 与相关迁移测试。
- 进程池按“成员”隔离，使同一个群里同一 Agent 的不同模型各自独立保活、独立回收。

## 7. 已核实的代码事实（2026-11-25 读源码）

- ACP 的 `SetPlanMode` 是空实现（`acp/session.go`），所以 ACP 类 Agent 目前没有“只读档位”。
- ACP 握手声明了 `Terminal: true`，但终端相关的五个回调都返回空对象（`acp/process.go`）。
- Windows 下 ACP 进程退出只调用 `proc.Kill()`；Unix 侧用进程组加 `SIGKILL`，两端不一致。
- Codex：启动 `app-server` 时没传 `thread_unload_delay_secs`，`Close()` 只关闭线程就返回。本机 codex 0.169.1 的二进制里有该配置项。它会不会造成终端 `codex resume` 冲突，**未验证**。
- `turndiff` 对整个工作区做前后快照对比，有大小上限，注释写明是“显示辅助”，失败只是不显示。
- 单聊切换 Agent 时，`prependSwitchHint` 会让模型读会话 jsonl 的尾部。群组里必须关闭它，否则盲评会泄题。
- 进程池键是 `<agent>-<sessionKey>`，同一会话里同一 Agent 不能同时跑两个不同模型，需要加成员维度。
- **未确认**：Antigravity 走不走 ACP；Claude 的 plan 模式和 Codex 的只读沙箱能否真的拦住写文件和 Bash。

## 8. 实施步骤与验证门槛

**步骤 0：验证核心前提（不写产品代码）**
- 拿一个作者真实遇到过的问题，用几个 CLI 按第 3 节流程手工跑一次，看第 2 轮出现的是真分歧还是互相附和。结果决定第 2 节要不要调整。
- 在临时目录里实测每个 Agent 在只读档位下能否改文件、能否用 Bash 改文件。
- 决策（作者 2026-11-25）：能只读的用原生只读；不能只读的，用“Reviewer 前后快照对比”事后检查兜底，发现改动就提示用户。

**步骤 A：底层修复**
- ACP 握手 `Terminal` 改为 `false`，补握手单测。
- Codex 两项（释放后线程锁、`thread/fork` 兼容）先在临时 `CODEX_HOME` 复现，未复现就不改代码。
- Windows 进程树：先评估 `taskkill /T` 是否够用，再决定是否上 Job Object。需要真实 Windows 验证后才能交付。

**步骤 B：群组底座**
成员槽位、进程池按成员隔离、`@点名`、控制块过滤器（移植）、文档保存与出处检查、迁移与旧库测试。

**步骤 C：讨论流程**
盲评、互评、轮次上限、暂停与插话、最终文档与确认。

**步骤 D：实现加群审**
主刀实现、基于 `turndiff` 的审阅材料、只读 Reviewer 的意见、用户同意后才改。

**步骤 E：界面**
建群与选成员、发言人标识、讨论状态条、文档查看。盲评时是否实时显示各成员输出等界面细节，到这一步再问作者。

每一步完成后，分别记录“源码完成”和“验证通过”，并写明验证范围，不沿用旧结论。

## 9. 不做的事

- 任务看板、任务编排、手势球等 mindfs 的重功能。
- 费用与用量展示、Prompt Cache 命中率展示、进程内存统计、JSONL 增量缓存、原地编辑最后一条消息（作者此前已明确不需要，或没有证据表明需要）。
- Reviewer 自动改代码；Reviewer 打回后的自动返工循环。
- 不依赖 Relay 部署新前端；群组界面资源随各自后台发布（见 AGENTS.md）。

## 10. 实现阶段由实现者自行处理的细节

- `turndiff` 会把用户自己的编辑也算进改动：只在审阅材料和界面上说明，不尝试过滤。
- `turndiff` 的结果分三种：有改动、没改动、没观察到。“没观察到”不能当“没改动”，事后检查和“主刀无改动则暂停”都要据此处理。
- 并行 Reviewer 的事后检查只能知道“工作区变了”，分不清是谁改的，提示用户即可。
- 发送锁、进程池键、迁移测试等工程细节。

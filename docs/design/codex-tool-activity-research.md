# Codex 风格工具活动展示调研

调研日期：2026-09-14。仓库基线：`main` / `a903fbe`。本机协议核验版本：`codex-cli 0.154.0`。

## 结论与证据边界

现有 Codex app-server 接入足以支撑接近参考截图的工具活动展示。主要工作是保留协议元数据、统一实时与历史摘要、调整前端信息层级。

本次搜索和阅读了 OpenAI 官方文档，核对了项目源码，并用本机 CLI 的 `app-server generate-ts` 生成协议类型进行验证。生成目录已清理，没有调用模型。

官方文档没有给出桌面端活动组件的完整源码、标题生成算法或折叠状态机。因此，下文明确区分截图观察、协议事实和建议实现，不能把建议宣称为桌面端内部实现。

## 截图能确认的行为

- 普通工具活动采用小图标、次级文字和紧凑单行布局，视觉上没有当前产品这种逐条圆角卡片边框。
- 摘要存在多种形式：泛化状态（运行了命令）、集成名称（Fastctx）、任务描述、耗时和截断的命令片段。
- 新截图仍然展示 `docker exec ...` 等命令片段，因此默认摘要不应全部替换成同一句泛化文案。
- 有展开箭头，长命令会截断；自然语言进展和最终回复保持更高的阅读优先级。
- 静态截图不能证明点击后的完整结构、连续调用的自动分组边界，也不能证明完成时是否会强制收起用户已展开的内容。
- “补齐同名数据卷并发保护并复测校验”等任务描述的来源尚未核实，不能认定由 `commandActions` 自动生成。

## 协议已提供什么

官方 [App Server 文档](https://developers.openai.com/codex/app-server) 定义了 Thread → Turn → Item 结构，以及 `item/started`、`item/completed`、输出增量和轮次完成事件。`item/completed` 是工具最终状态的依据。

本机生成的 0.154.0 TypeScript 类型进一步确认：

| 数据 | 用途 |
| --- | --- |
| `commandExecution.commandActions` | 识别 `read`、`listFiles`、`search`、`unknown`；字段中包含文件名、路径或查询词 |
| `commandExecution.command` / `cwd` | 保留完整命令及工作目录，供详情查看 |
| `status` / `exitCode` / `durationMs` | 生成正在运行、已完成、失败和耗时摘要 |
| `mcpToolCall.server` / `tool` / `durationMs` | 区分 MCP 调用及其来源；本机生成类型包含耗时字段 |
| `agentMessage.phase` | 可选地标记 `commentary` 与 `final_answer`，区分进展说明和最终回答 |

协议字段存在不代表每条事件一定有值。`durationMs`、`phase` 等缺失时应省略对应展示，不能编造耗时、任务含义或完成状态。

## 当前代码的具体差距

| 位置 | 已核实的问题或现有基础 |
| --- | --- |
| `runtime/server/internal/agent/codex/session.go`：`codexCommandTitle` | 即使识别出读取或搜索，也会把完整原始命令拼到自然语言摘要后；未知命令直接作为标题 |
| 同文件：`mapToolItem` | 接收到的 `commandActions` 只参与标题计算，没有作为结构化元数据继续传给前端 |

| `runtime/web/src/components/stream/ToolCallCard.tsx` | 默认已经折叠；折叠态仍使用整行边框、主文字颜色和原始标题。展开时按需加载详情的机制可以继续使用 |

| `runtime/web/src/components/SessionActivity.tsx` | 底部运行提示直接使用工具标题，也应采用相同的摘要规则 |

## 建议实现

### 1. 统一摘要与详情的数据职责

保持完整命令、参数和输出可追溯；用独立的展示规则生成简短活动摘要，不再把完整命令无条件拼入摘要。

摘要优先级建议：已存在且来源明确的任务描述 → 结构化读取/搜索动作 → 服务及工具名称或简短命令预览 → 通用状态。第一版无需额外调用模型生成标题。

普通命令预览可以简化已识别的 shell 包装并折叠换行；复杂脚本、引号或无法可靠解析的包装使用通用摘要或截断的原始预览。仅改变展示，不执行解析出的字符串，也不修改原始命令。

让实时事件、历史导入和已缓存的旧记录都经过同一个前端展示规则；后端保留结构化元数据。旧数据缺少动作或耗时时采用可用信息降级。

### 2. 使用轻量活动行

- 普通收起态：小型单色图标、次级文字、单行截断、紧邻摘要的展开入口；字号沿用 IDE 主题与缩放设置。
- 移除普通收起态卡片背景、边框和较强字重；保留适当点击区域与键盘焦点。
- 展开后显示完整命令、输出、目录、退出码等，日志区域限制高度并支持复制。
- `aria-expanded`、键盘操作、主题对比度和窄侧栏都应验证。
- 用户手动展开后，新输出或完成事件不应反复夺回其展开选择。

### 3. 按真实事件展示状态

| 状态 | 建议摘要示例 | 详情 |
| --- | --- | --- |
| 执行中 | 正在运行 `docker stats …` | 默认收起，可主动查看输出 |
| 已完成，有耗时 | 已在 1 秒内运行 `docker exec …` | 默认收起 |
| 已完成，无有效预览 | 运行了命令 | 点击看完整命令和结果 |
| 读取 / 搜索 | 已读取 README.md / 已搜索 session | 保留文件、查询等语义 |
| 失败 | 命令执行失败 · 退出码 1 | 保持失败状态可见，错误详情可展开 |
| 等待确认或回答 | 清楚展示待处理动作 | 不藏入普通完成活动组 |

这些是建议文案，并非已核实的桌面端固定文案或精确状态机。取消和中断也应保留真实状态，不能为了收起而改成成功。

### 4. 在活动行稳定后增加保守分组

可以把同一轮、同一段中连续且已完成的普通工具事件折叠成“执行了 8 项操作”，点击后显示活动行，再点击单项查看日志。

分组遇到进展说明、最终回答、用户消息、待审批或待回答项时终止；有明确父子关系时才展示调用嵌套，不能仅凭时间接近推断某条命令属于 Fastctx。

这是借鉴截图的信息组织方案，不是已证实的 Codex 自动分组算法。第一阶段优先完成单项摘要和样式，再评估分组是否需要默认启用。

## 验收重点

- 同一工具在实时接收、切换会话、刷新和历史导入后具有一致摘要与状态。
- shell 包装、长路径、多行脚本、读取、搜索、MCP、普通执行分别有合理的简短摘要，完整原文可查看。
- 输出增量更新已有调用，不能把轮询重复计为新命令；展开状态不被流式更新重置。
- 失败、取消、待审批和待回答不被普通活动折叠掩盖。
- 在 IDEA 窄侧栏、亮暗主题和实际缩放下检查布局；参考截图尺寸不同，不能直接用截图像素推断字号。
